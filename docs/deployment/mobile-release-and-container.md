# آماده‌سازی خروجی و استقرار

## Docker

از ریشهٔ مخزن بسازید تا داشبورد وب هم در تصویر قرار بگیرد:

```sh
docker build -f backend/Dockerfile -t safestep .
docker run --rm -p 4080:4080 \
  -e DATABASE_URL='postgres://…' \
  -e JWT_ACCESS_SECRET='…' \
  -e JWT_REFRESH_SECRET='…' \
  -e INVITE_CODE_PEPPER='…' \
  -e IDENTITY_DATA_ENCRYPTION_KEY='…' \
  safestep
```

پورت سرویس و داشبورد `4080` است. `DEMO_MODE` در تصویر خاموش است و باید
برای اجرای تولیدی رازهای بالا و نشانی PostgreSQL با مقادیر واقعی تزریق شوند.

## Android

شناسهٔ پیش‌فرض برنامه `ir.hamghadam.safestep` است. اگر ناشر شناسهٔ دیگری
دارد، آن را با `-PappApplicationId=...` هنگام build تعیین کند.

برای امضای انتشار، فایل محلی `mobile/android/key.properties` را از روی
`mobile/android/key.properties.example` بسازید و به یک keystore اختصاصی
اشاره دهید. فایل کلید و گذرواژه را وارد Git نکنید. build انتشار بدون این
فایل امضای debug را به‌کار نمی‌برد و APK خروجی امضانشده خواهد بود.

```sh
cd mobile
flutter build apk --release
```

HTTP ساده مجاز است فقط در manifest گونهٔ debug برای اتصال به سرور محلی؛
در manifest اصلی و نسخهٔ release غیرفعال است.

## پیش‌نیاز آزمایش میدانی

برای دسترسی ده خانواده از بیرون شبکهٔ محلی، کارفرما یا مسئول استقرار باید
یک سرور عمومی با دامنه‌ای تحت اختیار خود، گواهی معتبر HTTPS، دسترسی مدیریتی
به سرور و پایگاه PostgreSQL، پشتیبان‌گیری و راه بازیابی فراهم کند. نقطهٔ
شروع پیشنهادی برای این مقیاس کوچک یک ماشین Linux با ۲ هسته، ۴ گیگابایت RAM،
حداقل ۴۰ گیگابایت فضای SSD، Docker و دسترسی ورودی HTTPS روی پورت ۴۴۳ است؛
ظرفیت نهایی باید با بار واقعی و رشد داده سنجیده شود. سرویس Node و PostgreSQL
را مستقیماً به اینترنت عمومی باز نکنید؛ پروکسی HTTPS را جلوی برنامه قرار دهید.
نشانی عمومی و زمان استقرار هنوز تعیین نشده‌اند.

مهاجرت‌های ۰۱۶ تا ۰۱۸ ناظر اصلی تکراری را اصلاح و یکتا می‌کنند. اگر چند
رابطهٔ فعال پرچم ناظر اصلی داشته باشند، جدیدترین رابطه حفظ می‌شود و ردیف
اصلی هر پرچم تغییرکرده در `supervisor_flag_cleanup_archive` نگهداری می‌شود؛
پرچم رابطهٔ قطع‌شده نیز پاک می‌شود. پیش از مهاجرت نسخهٔ پشتیبان بگیرید و
پس از آن موارد آرشیوشده را با مسئول پروژه بررسی کنید. ساخت index در روش
فعلی مهاجرت تراکنشی است و ممکن است نوشتن روی جدول را مسدود کند؛ در پنجرهٔ
نگه‌داری اجرا شود. بازگردانی انتخاب ناظر نیازمند تصمیم مسئول داده و مهاجرت
یا اصلاح کنترل‌شدهٔ بعدی است.

کلید `IDENTITY_DATA_ENCRYPTION_KEY` باید پیش از اجرای مهاجرت و راه‌اندازی
سرور همان کلیدی باشد که داده‌های موجود با آن رمز شده‌اند. مهاجرت در production
رازهای پیش‌فرض را رد می‌کند و در صورت وجود ciphertext یک نمونه را پیش از
تغییر schema یا رمزکردن دادهٔ قدیمی باز می‌کند؛ خطا مانع ادامه می‌شود. نبود
نمونه به معنی تأیید کلید نیست و موفقیت یک نمونه سلامت همهٔ ردیف‌ها را ثابت
نمی‌کند. تعویض کلید به برنامهٔ بازرمزگذاری و پشتیبان قابل بازیابی نیاز دارد.

مدیر احرازشده می‌تواند از مسیر `GET /api/v1/evaluation/export/{dataset}`
فایل CSV پنج مجموعهٔ `location_reference_samples`، `sus_responses`،
`alert_deliveries`، `fall_events` و `location_telemetry` را دریافت کند.
مختصات و نام حساب‌ها صادر نمی‌شوند، ولی شناسه‌های کاربر همچنان قابل پیوند
هستند و فایل‌ها باید محدود نگه داشته شوند. نام نقطهٔ مرجع متنی است که کاربر
وارد می‌کند؛ نام اشخاص یا اطلاعات شناسایی‌کننده در آن وارد نشود. پاسخ SUS
آخرین ردیف هر کاربر است و دادهٔ مکان صرفاً منبع device را همراه پرچم
`is_queued_replay` برمی‌گرداند. `latency_ms` زمان واگذاری به کانال است؛
`device_receipt_recorded_at` و `alert_to_server_receipt_ms` زمان callback خوداظهاری
ثبت‌شده در سرور را نشان می‌دهند و زمان نمایش روی گوشی را ثابت نمی‌کنند.

`npm run seed` داده‌ها و حساب‌های دمو را بازسازی می‌کند و در production به‌طور
پیش‌فرض متوقف می‌شود. تنها override صریح `npm run seed -- --allow-production-seed`
است؛ این دستور داده‌های دمو را حذف و دوباره می‌سازد و برای پایگاه آزمایش واقعی
یا تولید توصیه نمی‌شود.

در محیط واقعی `NODE_ENV=production` و `DEMO_MODE=false` را تنظیم کنید،
`CORS_ORIGINS` را با مبدأهای مجاز وب و رازهای منحصربه‌فرد را از محیط امن
فراهم کنید. نسخهٔ release فقط نشانی `https://` با گواهی قابل‌اعتماد دستگاه
را می‌پذیرد. Firebase و آزمون تحویل روی گوشی نیز پیکربندی و دستگاه واقعی
لازم دارند.

پروکسی باید `Host` واقعی را حفظ و `X-Forwarded-Proto` ورودی را بازنویسی کند؛
برنامه یک hop پروکسی را قابل اعتماد فرض می‌کند. پورت داخلی برنامه فقط از
پروکسی قابل دسترس باشد تا کلاینت نتواند هدر پروکسی را جعل کند.

مالک برنامه می‌تواند کلید انتشار اختصاصی را با دستور زیر بسازد؛ ابزار به‌صورت
تعاملی گذرواژه و مشخصات گواهی را می‌پرسد. گذرواژه را در خط فرمان، مخزن یا
بستهٔ عمومی ننویسید و نسخهٔ پشتیبان کلید و گذرواژه را جداگانه نزد مالک نگه دارید.

```sh
keytool -genkeypair -v -keystore safestep-release.jks -alias safestep -keyalg RSA -keysize 3072 -validity 10000
```

سپس مسیر keystore، alias و گذرواژه‌ها را در `mobile/android/key.properties`
محلی بر اساس فایل نمونه قرار دهید و build انتشار را انجام دهید. امضای فایل را
با `apksigner verify --verbose --print-certs <path-to-release.apk>` کنترل کنید.
نسخهٔ unsigned فعلی قابل ارائه به‌عنوان APK امضاشده نیست.
